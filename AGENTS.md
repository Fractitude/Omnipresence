# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## The game

**Omnipresence in the Wired** is a game inspired by *Serial Experiments Lain*.

## What this is

An s&box game project (project title "Omnipresence", package `fractitude.omnipresence`), created from the s&box player-controller template. Multiplayer game type (up to 64 players, tick rate 50). Startup scene: `Assets/scenes/playground.scene`. Gameplay code is still template-level.

Use the `sbox` skill for s&box engine/editor specifics. `omnipresence.sbproj` enables MCP communication with the s&box editor (`"AI": { "EnableMcpCommunication": true }`).

## Building and running

- There is no CLI build, lint, or test step. The s&box editor compiles `Code/` and `Editor/` and hot-reloads on save. Compile errors show in the editor console.
- The `.csproj` / `.slnx` files are **generated by the editor** and git-ignored. Do not edit them by hand. They point at the Steam install (`C:\Program Files (x86)\Steam\steamapps\common\sbox`) for engine references and build output.
- Run the game with Play in the s&box editor. Open `omnipresence.sbproj` in the editor to load the project.

## Editing scenes, prefabs and inspector values

- **Never change scenes, prefabs or inspector values while the game is in play mode**, unless the user asked to try values out in play mode. Play-mode changes are runtime state and are lost, or worse, get saved into the asset. Stop play first (`play_stop`), then edit.
- **Don't hand-edit `.scene` or `.prefab` JSON while the editor has the project open.** The editor writes its own copy back and puts runtime state in it (a `local_player` tag, regenerated guids), which broke the player controller's setup once. Use the editor's tools through `sbox-cli` (`create_game_object`, the component tools, `asset_write`). If you must edit the file, check `git diff` afterwards for changes you didn't make.

## Layout

- `Code/` — runtime game code (assembly `omnipresence`, root namespace `Sandbox`). `Assembly.cs` holds global usings (`Sandbox`, `System.Collections.Generic`, `System.Linq`). Razor (`.razor`) UI is supported.
- `Addons/` — Navi Store apps as addon projects (`navi_pacman`). Not compiled by this game; each is its own s&box project. See "Navi Store apps" below.
- `Editor/` — editor-only tooling (global usings add `Editor`). Excluded from the runtime assembly. Never reference `Editor` types from `Code/`.
- `Assets/` — scenes and other assets. `.scene` files are JSON; components are referenced by `__type` (custom components by class name, e.g. `Sandbox.NaviComputer`). Renaming a component class breaks scene references.
- `ProjectSettings/` — `Input.config` defines input action names used by `Input.Down("Run")` etc.; `Collision.config` defines collision layers.
- `Libraries/` — s&box library packages. `Libraries/navi/` is the Navi computer (`fractitude.navi`), a git submodule of `git@github.com:Fractitude/Navi.git` (clone with `--recurse-submodules`; commit library changes in that repo first): OS (`NaviComputer`), desktop UI (`NaviDesktop`), the app system and built-in apps. It is our own library, made to be installed in other games too; see `Libraries/navi/README.md`. Libraries can't reference game code.
- `docs/console-commands.md` lists every console command. When you add, rename or remove a `[ConCmd]`, update it.

## Navi Store apps

- **Always prefix a Navi app's package ident with `napp_`**, e.g. `fractitude.napp_pacman`. This is the ident set when publishing the app's `.napp` asset, not the addon project's own ident.
- Store apps are addons that target the Navi library (`ParentPackage` is `fractitude.navi` in the `.sbproj` and the `.napp`'s meta), never a game: an app must have no notion that Omnipresence exists. Their code must not use Navi types and the addon must not install the Navi library, or the published package bundles its own Navi. They talk to the computer through a copy of the `Navi` client (`Libraries/navi/Code/Navi/Client/Navi.cs`). See `Libraries/navi/README.md`.
- Every app, built-in or Store, is a `.napp` manifest plus a panel that uses the `Navi` client, split into a `ViewModel` that holds the logic and a `UiState` the panel draws statelessly (`Libraries/navi/docs/app-architecture.md`). Declare the permissions an app needs in its manifest. `IsSystem` asks for root (full system access): pre-packaged system apps have it, Store ones ask the player when installed. The window shield means root and nothing else.
- Publish apps under the `fractitude` org; the Store marks them as official.
- Publishing a Store app: publish the Navi library first if it changed (open `Libraries/navi/navi.sbproj`, normal Publish), restart the addon editor, then right-click the `.napp` in the addon's Asset Browser and choose **Publish** (ident `napp_<name>`). A package without code makes the game log `has no panel class`; it happened when the addon was on an old Navi (the `.napp` type then didn't include code). Batch Publish is untested with a current Navi. A good package has the code (`.cll`); Pac-Man's has 5 files. If the editor says "Can't publish" or shows stale or foreign assets, close the addon editor and delete its `.sbox/cloud` and `.sbox/cloud.db`. Each publish gets the next version number by itself. Details are in `Libraries/navi/README.md`.

## Weapons

Ported from Facepunch's open-source sandbox game (`github.com/Facepunch/sandbox`), whose M4a1 is the reference. Ballistics, ammo, reload, the view model and world model lifecycle live in the **engine** (`BaseCombatWeapon`, `BaseInventoryComponent`, `BaseWeaponModel`); `Code/Weapons/` is the game layer on top, kept close to Facepunch's files so upstream changes diff cleanly.

- `Base/BaseSandboxWeapon*.cs` is trimmed (no seats, NPCs, kill icons or their `Player` type; `Owner` is the engine's `PlayerController`). `BaseBulletWeapon` adds recoil, `IronSightsWeapon` aim down sights, `MeleeWeapon` swings, `ProjectileEntity` is the base of rockets and launcher grenades. `ViewModel/` drives the first-person arms. Weapons: M4a1, Colt1911, Glock, Revolver, Mp5 (with grenade launcher), Shotgun, Sniper (scope shader `Assets/shaders/postprocess/sniper_scope.shader`), Rpg, HandGrenade, Crowbar, Camera (render-target camera held in hand), Physgun (`PhysGun/`, with the `PrefabSpawner` its effects need, written here because upstream has none).
- `WeaponInventory` is the hotbar on the player prefab. It is separate from the grid `PlayerInventory`. Slot keys, `Drop` and the `Slot…` input actions are read there.
- Weapon prefabs live in `Assets/weapons/<name>/` (`<name>.prefab`, `_vm` view model, `_wm` world model). The models are Facepunch cloud packages (`facepunch.w_m4a1`, `v_m4a1`, `rifle_muzzleflash`, `v_first_person_arms_human`); `install_package` them. Some sounds come from cloud packages too (the revolver's `rust.python…`). When a prefab logs a missing `.vsnd_c` or `.vmdl_c`, read `__references` in the file and install that package.
- Bullets trace with the `bullet` collision rule (`ProjectSettings/Collision.config`).
- Upstream hooks that need seats, NPCs or the `Player` type (`OnPrimaryPressed`, `OnCameraMove`, `OnPlayerDeath`, contraption inputs, `ImpactPrefab`'s direction argument) were dropped when porting. Scope sensitivity uses `PlayerController.LookSensitivity`.
- **Leave `GiveOnStart` off on the player prefab's `WeaponInventory`** and turn `UsesLoadout` on: the engine's start-up grant made `PlayerController` throw a NullReferenceException while it was created. `WeaponInventory` grants the loadout itself 0.1 s later.

## Security

**Always think about privilege escalation attacks.** For every change to Navi, ask how an app could use it to get permissions or root it wasn't granted, to act as another app, or to act without the player's consent. Assume Store apps are written by a stranger who wants that.

- **Consent prompts live only in the secure layer** (`NaviSecurePrompt`), like Windows' secure desktop:
  - It is its own panel, in front of the screen, so it draws above everything and gets clicks first.
  - While a prompt is open it covers the screen, so apps can't be clicked.
  - Apps can't reach it through their panel's ancestors.
  - Its controls react only to a real mouse press (`Input.Keyboard.Down( "MOUSE1" )`, which game code can't fake), made after the prompt has been up for `ArmTime`, and released on the same control.
  - Never show a consent prompt in the desktop or in an app panel, and never add a way to answer one without real player input.
- **The lock screen lives in the secure layer too.** While `NaviComputer.IsLocked`, `Authorize` refuses every `User…` RPC except sit, keep-seat, leave and unlock. Without a password the player who locked it unlocks with a real press (`LockOwner`). With a password or pattern (`NaviLockKind`), it is typed or drawn only in `NaviLockEntry`, inside the secure layer, on the client of the player in the seat: it is never synced, never shown to anyone else, and never sent. The client turns it into a proof (`NaviLockCrypto`: salted PBKDF2-HMAC-SHA256) and only that goes to the host with `UserUnlockWith`/`UserSetLock`; the host keeps the salt and a hash of the proof, and the hash never leaves it (`CaptureSave( secrets: false )` for snapshots). Wrong tries are counted and delayed by the host for each connection, so one player's guesses never make another wait. While one is typed, `SecureEntryActive` stops the player's keys being forwarded to any app. Not protected: hostile code in the game (see the known limit below) can read the client's memory, or change the host's state.
- **App calls go through `NaviSystemCalls`**, which runs as the calling window. Check permissions there. Never trust what an app says about who it is, and don't give apps a reference to Navi objects.
- **Multiplayer: the host runs the computer.** Clients only draw its snapshot. What a player does on the screen reaches the host as a `User…` RPC on `NaviComputer`, which must check the caller is the seated user (`Authorize`, from `Rpc.Caller`). Never let a client send state, make app calls, or answer a prompt without the seat. A viewer's copy of a shared app makes no calls.
  - Known limit: the host trusts the user's client that a prompt answer came from a real press. A modified client can fake it, for its own seat only. A hostile host can make clients download any Store app, and open any panel class in their code as an app (clients without the game's `.napp` files take the host's manifests).
- **Plugins are part of the OS, and only the host installs them** (`NaviPluginManager`). They run with no sandbox, permissions or prompt, so the host's choice is the only gate: never add a way for a client, an app or a `User…` RPC to install, remove or toggle one, and keep the console commands refusing to run unless `NaviPluginManager.CanManage`. Clients run the plugins the host announces.
- **Files: an app without `navi.files.access` has only its own folder** (`/Library/Apps/{app id}`). `NaviFileCalls` checks every path twice: as the app wrote it, before anything is looked up (so it can't learn what exists outside), and where it leads with symlinks followed (so a link in its folder can't reach out). Any new `files.*` call must do both. Restoring from the trash and ejecting a drive need the permission. Only the host has the files; they are never sent to clients.
- **The file picker is a system window, not part of the app.** `Navi.Files.PickAsync` (`files.pick`, no permission needed) makes the computer open the File Picker (`navi/apps/filepicker.napp`, a core app: root, never in the start menu, no app can `apps.launch` it, always opaque). Only that app may make the `picker.*` calls (`NaviSystemCalls` checks the caller's id), and they only answer the one request waiting (`NaviComputer.Picker.cs`). The chosen file goes into the caller's `NaviProcess.PickedFiles`, which `NaviFileCalls` honours for **reading that exact path only** (`read: true`, never write, move or delete, never its folder or its siblings). The caller only gets a path back; it never sees a folder listing. Closing the picker or the caller answers with null. Never let an app pass a path to `picker.choose`, add a way to grant `PickedFiles` outside `AnswerPick`, or draw the picker inside an app's panel. Known limit, as for every window: hostile code in the game can fake the choice (it can already change the computer's state).
- **Messages belong to a player, not to an app or a computer.** `NaviMessages` keeps them on the host. Every `messages.*` call (`NaviMessageCalls`) needs `navi.messages.access`, runs on the host, and is asked as the player in the computer's seat, worked out from the connection (`NaviMessages.Identify`). Never take the player, or a "from", from an app's arguments, and never add a call that reads a thread or sends as a player other than the seat's. Messages are saved on the host and never sent to clients except as a shared app's state (the open conversation), which every player near the screen gets.
- **Game NPCs in Messages are the game's voice** (`NaviNpcs`). Only game code makes them and speaks for them (`NaviNpc.Send`, `Edit`, …); no `messages.*` call or `User…` RPC may send as an NPC, edit or delete its messages, or register one. An app may message an NPC as the seated player, and the text that reaches `NaviNpc.Received` is that player's: the game must not trust it. A hidden NPC refuses a player's message until it has written to them first.
- **Notifications are drawn by the desktop.** An app gives only a title and text (`navi.notifications.post`); its name and icon come from its manifest, so it can't pass for another app or the system. It dismisses only its own, and can't unmute itself (core apps can, as the OS).
- **Store apps are untrusted.** Only pre-packaged apps are part of the OS. A Store app gets root only after the player accepts it in the secure layer.
- **Known limit: s&box gives every package's code the same sandbox.** `TypeLibrary` exposes even private members of package (`package.*`) code, so a hostile Store app can find `NaviComputer` and change its state directly, skipping permissions and prompts.
  - Navi's permissions stop honest-but-careless apps and UI tricks: fake clicks, overlays, pre-ticked boxes. They don't stop hostile code. Don't claim more than that in UI or docs.
  - What helps against hostile code: the Store's official badge, published code being readable, and the root consent at install.

## Architecture

s&box uses a scene/GameObject/Component model. Gameplay is written as `Component` subclasses that override lifecycle hooks (`OnUpdate`, `OnFixedUpdate`, `OnPreRender`, …). Movement is handled by the engine's built-in `PlayerController` with `MoveMode*` components. A custom component can drive it by setting `WishVelocity` / `EyeAngles` and pull it in with `[RequireComponent]`.

### Static state and hot reload

**Never make static state that changes at run time `readonly`, including get-only auto-properties (`{ get; } = new()`).** A hot reload resets a `static readonly` field to its initial value when its type holds only engine or BCL types (`string`, numbers, `HashSet<string>`, `Dictionary<string, long>`). Fields that aren't readonly keep their values, and so do readonly ones that hold the assembly's own types. Use `static Dictionary<…> x = new()` or `{ get; private set; } = new()`. Constants (lookup tables nobody changes) can stay readonly, since a reset only picks up edits. Instance fields aren't affected: a readonly instance field keeps its value.

Losing such a field fails silently. Navi lost its map of downloaded Store apps this way, so installed Store apps vanished from the start menu, and it also lost the game's Store allowlist. To check a change, set the state, force a reload (edit a file in the same assembly), and read it back with `sbox-cli --call run_csharp`.

### UI pitfalls

Found building the Character menu (`Code/Character/`). Each one froze the editor, closed the menu at once or left the player without controls.

- **A `ScenePanel` with no `RenderScene` ticks the game scene**, which runs the panel's own component again, in itself. Build the scene before the panel exists and pass it as an attribute (`<ScenePanel RenderScene=@scene/>`). Never destroy a scene while a panel still draws it.
- **A `new Scene()` starts every `GameObjectSystem` in it**, so a system that makes a HUD makes one there too (a second menu that shares `static` state and closes the first). Skip it: see `CharacterMenu.PreviewScene` in `AbilitySystem`.
- **`Input` mouse buttons read false while the cursor is over a panel that takes the mouse**, and `HasActive`/`HasHovered` can stay false. Use the panel's events (`@onmousedown`, `@onmouseup`, `@onclick`), as `AbilityMenu` does.
- **A panel's event handlers and its component's `OnUpdate` were not on the same instance.** State they share must be `static`.
- **Turning off `UseInputControls` leaves `WishVelocity` as it was**, so a held key walks on. Set `WishVelocity = 0` every frame while it is off, as `NaviInputCapture` does.
- **Removing a `GameObjectSystem` class** makes the open editor log an error every frame until it restarts.
- **The editor's console buffer and `sbox-dev.log` lag behind a hang.** To debug one, write lines to `FileSystem.Data` at once (the game's data folder under the engine's `data/`), and remove them when done. Tests that call private methods through `run_csharp` can freeze the editor: press the real key.

## Code style

`docs/code-style.md` is the contract: Rider's **default** code style settings over the repo's `.editorconfig`, which is what formats the files in `Code/`, `Editor/`, `Addons/` and `Libraries/navi/Code/`. Run Reformat Code (Ctrl+Alt+L) on the files you touch before committing.

- Tabs, 4 wide, CRLF, final newline. Braces on new lines (Allman).
- Spaces inside parentheses for calls and control flow, e.g. `Input.Down( "Run" )`, `if ( x > 0 )`; no spaces inside casts, grouping parens, `nameof(...)` or target-typed `new(...)`.
- Razor inline expressions are spaced: `@( entry.Expanded ? "Less" : "More" )`.
- 120 columns. The doc covers where a line breaks and how: Razor attributes wrap aligned under the first attribute, LINQ chains get one call per line, collection expressions open on the next line.

## Git commits

When you finish a piece of work, commit it, without waiting to be asked. Stage only the files you changed for that work, never unrelated changes already in the working tree. Format the files you touched first (see Code style).

## Git ignores

Generated files are ignored: `*.csproj`, `*.slnx`, `.sbox/`, compiled assets (`*_c`, except `*.shader_c`), `launchSettings.json`, `Exports/`.
