# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## The game

**Omnipresence in the Wired** is a game inspired by *Serial Experiments Lain*.

## What this is

An s&box game project (project title "Omnipresence", package `fractitude.omnipresence`), created from the s&box player-controller template. Multiplayer game type (up to 64 players, tick rate 50). Startup scene: `Assets/scenes/playground.scene`. Gameplay code is still template-level.

Use the `sbox` skill for s&box engine/editor specifics. `omnipresence.sbproj` enables MCP communication with the s&box editor (`"AI": { "EnableMcpCommunication": true }`).

## Building and running

- There is no CLI build, lint, or test step. The s&box editor compiles `Code/` and `Editor/` and hot-reloads on save. Compile errors show in the editor console.
- The `.csproj` / `.slnx` files are **generated by the editor** and git-ignored. Do not edit them by hand. They point at the Steam install (`C:\Program Files (x86)\Steam\steamapps\common\sbox`) for engine references and build output.
- Run the game with Play in the s&box editor. Open `omnipresence.sbproj` in the editor to load the project.

## Editing scenes, prefabs and inspector values

- **Never change scenes, prefabs or inspector values while the game is in play mode**, unless the user asked to try values out in play mode. Play-mode changes are runtime state and are lost, or worse, get saved into the asset. Stop play first (`play_stop`), then edit.
- **Don't hand-edit `.scene` or `.prefab` JSON while the editor has the project open.** The editor writes its own copy back and puts runtime state in it (a `local_player` tag, regenerated guids), which broke the player controller's setup once. Use the editor's tools through `sbox-cli` (`create_game_object`, the component tools, `asset_write`). If you must edit the file, check `git diff` afterwards for changes you didn't make.
- **A child of a network object is only sent to clients if it is Network Mode Snapshot (or Object), never Never.** The engine builds each client's copy of a network object from its networked children alone: a `Never` child — the model, the collider — never arrives, so the client gets the object with no children at all, and it is invisible and cannot be looked at or used. The root stays Object; the children a client must have are Snapshot, as `mailbox.prefab` has them. This is why the storage box, the grow tray, the press bench, the packing table and every dropped world item were host-only. A child a component creates itself at run time is not affected.

## Layout

- `Code/` — runtime game code (assembly `omnipresence`, root namespace `Sandbox`). `Assembly.cs` holds global usings (`Sandbox`, `System.Collections.Generic`, `System.Linq`). Razor (`.razor`) UI is supported.
- `Addons/` — Navi Store apps as addon projects (`navi_pacman`). Not compiled by this game; each is its own s&box project. See "Navi Store apps" below.
- `Editor/` — editor-only tooling (global usings add `Editor`). Excluded from the runtime assembly. Never reference `Editor` types from `Code/`.
- `Assets/` — scenes and other assets. `.scene` files are JSON; components are referenced by `__type` (custom components by class name, e.g. `Sandbox.NaviComputer`). Renaming a component class breaks scene references.
- `ProjectSettings/` — `Input.config` defines input action names used by `Input.Down("Run")` etc.; `Collision.config` defines collision layers.
- `Libraries/` — s&box library packages. `Libraries/navi/` is the Navi computer (`fractitude.navi`), a git submodule of `git@github.com:Fractitude/Navi.git` (clone with `--recurse-submodules`; commit library changes in that repo first): OS (`NaviComputer`), desktop UI (`NaviDesktop`), the app system and built-in apps. It is our own library, made to be installed in other games too; see `Libraries/navi/README.md`. Libraries can't reference game code.
- `docs/scripting.md` is what we know about the engine's experimental run-time scripting (`Game.Scripting`, Breen): the API, the language, and what a script can reach in this game. Read it before adding any script feature to Navi or the game; update it when you test more.
- `docs/ui.md` is how the HUD and the menu windows are built: one HUD GameObject that `HudSystem` puts every runtime piece on (`hud.Attach<T>()`, one line each, ordered by CSS `z-index`), and `MenuWindow`, the one window every menu uses (size cap, ability bar clearance, scrolling lists, rows that don't shrink). Read it before adding a menu or a HUD piece.
- `docs/world-items.md` is how an item is dropped into the world and picked up again (`WorldItem`, `PickupRules`, the merge rule `StackRules.CanMerge`). Read it before changing the inventory's add, drop or stack code.
- `docs/organizations.md` is how organizations work: teammates grouped in the Organizations Navi app, with roles, shares and invitations, and `OrgPayouts.Distribute`, the one function a revenue source calls to share a payment. Read it before adding a source of money.
- `docs/depot.md` is how big objects (storage box, grow tray, press bench, packing table) are bought in the Depot app, delivered and kept between sessions (`Code/Placeables/`, `PlacedObject` ids). Read it before adding something the player places in the world.
- `docs/stats.md` is the server's log of what players do over time (joins, playtime, kills, deaths, every money movement, purchases, kicks, bans): `StatsLog`, the files it writes and how to log a new source of money. Read it before adding a source or sink of money, a purchase or a way to remove a player.
- `docs/console-commands.md` lists every console command. When you add, rename or remove a `[ConCmd]`, update it.

## Vehicles

Ported from Facepunch's open-source sandbox game (`github.com/Facepunch/sandbox`, MIT), like the weapons. `Code/Vehicles/` is `FourWheelVehicle` (a rigidbody whose wheels are raycast suspension, posed from the model's bones; see `Assets/vehicles/buggy/RIG.md`), `VehicleCamera`, `VehicleSounds` and `VehicleLights`, kept close to upstream. `Code/Vehicles/Control/` is the seat control from upstream's ControlSystem: on the host, `ControlSystem` calls `IPlayerControllable.OnControl` on everything in the contraption of an occupied engine `BaseChair` (`LinkedGameObjectBuilder` follows physics joints), with the seated player's keys readable through `ClientInput`. Weapons are controllable too: a weapon with `ShootInput`/`SecondaryInput` set and no owner fires from a seat. `WeaponInventory` holsters the held weapon when its player sits in any `ISitTarget` and brings it back on getting up (`ISeatHolsterEvents` can cancel). The headlights are read on the driver's own machine (`VehicleLights`, F) and asked of the host by RPC. Not ported: the tuning HUD, the seated third-person orbit camera, `ManualLink` and signal wiring. Vehicle materials come from cloud packages (`facepunch.tractorwheel`, `carseat`, `beer_keg_a1`, `tyre`), listed in the buggy prefab's `__references`. `spawn_buggy` spawns the buggy.

## Navi Store apps

- **Always prefix a Navi app's package ident with `napp_`**, e.g. `fractitude.napp_pacman`. This is the ident set when publishing the app's `.napp` asset, not the addon project's own ident.
- Store apps are addons that target the Navi library (`ParentPackage` is `fractitude.navi` in the `.sbproj` and the `.napp`'s meta), never a game: an app must have no notion that Omnipresence exists. Their code must not use Navi types and the addon must not install the Navi library, or the published package bundles its own Navi. They talk to the computer through a copy of the `Navi` client (`Libraries/navi/Code/Navi/Client/Navi.cs`). See `Libraries/navi/README.md`.
- Every app, built-in or Store, is a `.napp` manifest plus a panel that uses the `Navi` client, split into a `ViewModel` that holds the logic and a `UiState` the panel draws statelessly (`Libraries/navi/docs/app-architecture.md`). Declare the permissions an app needs in its manifest. `IsSystem` asks for root (full system access): pre-packaged system apps have it, Store ones ask the player when installed. The window shield means root and nothing else.
- Publish apps under the `fractitude` org; the Store marks them as official.
- Publishing a Store app: publish the Navi library first if it changed (open `Libraries/navi/navi.sbproj`, normal Publish), restart the addon editor, then right-click the `.napp` in the addon's Asset Browser and choose **Publish** (ident `napp_<name>`). A package without code makes the game log `has no panel class`; it happened when the addon was on an old Navi (the `.napp` type then didn't include code). Batch Publish is untested with a current Navi. A good package has the code (`.cll`); Pac-Man's has 5 files. If the editor says "Can't publish" or shows stale or foreign assets, close the addon editor and delete its `.sbox/cloud` and `.sbox/cloud.db`. Each publish gets the next version number by itself. Details are in `Libraries/navi/README.md`.

## Weapons

Ported from Facepunch's open-source sandbox game (`github.com/Facepunch/sandbox`), whose M4a1 is the reference. Ballistics, ammo, reload, the view model and world model lifecycle live in the **engine** (`BaseCombatWeapon`, `BaseInventoryComponent`, `BaseWeaponModel`); `Code/Weapons/` is the game layer on top, kept close to Facepunch's files so upstream changes diff cleanly.

- `Base/BaseSandboxWeapon*.cs` is trimmed (no seats, NPCs, kill icons or their `Player` type; `Owner` is the engine's `PlayerController`). `BaseBulletWeapon` adds recoil, `IronSightsWeapon` aim down sights, `MeleeWeapon` swings, `ProjectileEntity` is the base of rockets and launcher grenades. `ViewModel/` drives the first-person arms. Weapons: M4a1, Colt1911, Glock, Revolver, Mp5 (with grenade launcher), Shotgun, Sniper (scope shader `Assets/shaders/postprocess/sniper_scope.shader`), Rpg, HandGrenade, Crowbar, Camera (render-target camera held in hand), Physgun (`PhysGun/`, with the `PrefabSpawner` its effects need, written here because upstream has none).
- `WeaponInventory` is the hotbar on the player prefab. It is separate from the grid `PlayerInventory`. Slot keys, `Drop` and the `Slot…` input actions are read there.
- Weapon prefabs live in `Assets/weapons/<name>/` (`<name>.prefab`, `_vm` view model, `_wm` world model). The models are Facepunch cloud packages (`facepunch.w_m4a1`, `v_m4a1`, `rifle_muzzleflash`, `v_first_person_arms_human`); `install_package` them. Some sounds come from cloud packages too (the revolver's `rust.python…`). When a prefab logs a missing `.vsnd_c` or `.vmdl_c`, read `__references` in the file and install that package.
- Bullets trace with the `bullet` collision rule (`ProjectSettings/Collision.config`).
- Upstream hooks that need seats, NPCs or the `Player` type (`OnPrimaryPressed`, `OnCameraMove`, `OnPlayerDeath`, contraption inputs, `ImpactPrefab`'s direction argument) were dropped when porting. Scope sensitivity uses `PlayerController.LookSensitivity`.
- **Leave `GiveOnStart` off on the player prefab's `WeaponInventory`** and turn `UsesLoadout` on: the engine's start-up grant made `PlayerController` throw a NullReferenceException while it was created. `WeaponInventory` grants the loadout itself 0.1 s later.

## Health

Ported from Facepunch's open-source sandbox game (`Player.cs`, `GameManager.cs`, `PlayerFallDamage`, `HealthPickup`), in `Code/Health/` (the player's health, fall damage, HUD, pickup) and `Code/Game/` (`GameManager`, `PlayerData`, events, observer). The engine only gives `Component.IDamageable` and `DamageInfo`; the health is ours.

- `PlayerHealth` is on the player prefab: `Health`, `MaxHealth`, `Armour` (synced from the host), `OnDamage` (host only: spawn protection, god mode, `OnDamaging` event that can cancel or change damage, headshot x2, armour first), then `Kill`: ragdoll, observer, destroy the player.
- `GameManager` is a `GameObjectSystem`, so the engine makes it in every scene and nothing needs to carry it. It is a small version of upstream's: `PlayerData` per connection (kills, deaths, god mode), `SpawnPlayer`, `Respawn`, `RequestRespawn` (from `PlayerObserver`) and `OnDeath`. The first spawn is still the scene's `NetworkHelper`; respawns use its player prefab and spawn points.
- Events are `Local.IPlayerEvents` and `Global.IPlayerEvents` (`PlayerEvents.cs`), the subset health needs. Fall damage comes from `PlayerController.IEvents.OnLanded` in `PlayerFallDamage`.
- `HealthHud` (bottom left, like `AmmoHud`) is put on the HUD object by `HudSystem`. `PlayerDamageIndicators` paints the red direction arrows.
- `GameManager` also: out-of-bounds bodies are destroyed, `SpawnPlacement` picks a free, floor-settled spawn point (not the last one used), `Notify( text )` and `Kick` (`GameManager.Util.cs`; the `kick` command is the engine's), and `GameManager.PropImpactShake.cs` shakes nearby cameras when a prop hits the world (scaled by `omni.screenshake`).
- Not ported: Steam stats, the kill feed, gibs, `HudElement` hiding, upstream's spawn, material and morph RPCs, `LimitsSystem`, `ServerSettings`, `CleanupSystem`.

## Security cameras

`SecurityCamera` (`Code/Security/`) is on the prefab `Assets/security/camera.prefab`, a wall camera made of boxes: the root is the camera's aim (+X forward, the `Lens Camera` child holds the `CameraComponent` the feed is drawn through), and `spawn_security_camera` puts one where you stand. A camera draws only while an app asks for its picture, and stops a second after the last ask (`RequestFeed`, `OnPreRender`), so one nobody watches costs nothing.

The **Security System** app (`Code/Apps/Security/`, `Assets/navi/system/security.napp`) connects to every camera within `SignalRange` of the computer (1500 units, about 38 m) and shows the feeds in a grid. Clicking a camera enlarges it and lists the others in a scrolling panel on its left, each row a live preview of that camera; "All cameras" goes back to the grid. It is shared, so the host's copy holds the list and which camera is enlarged, and every player near the screen sees the same one. See [security.md](docs/security.md).

- **The picture never crosses the network.** Each client draws its own feed from its own copy of the world and of the camera, so a shared app's viewers see live pictures with no texture sync. The state carries only each camera's object id (the same on every machine); `SecurityFeeds`, in the panel, finds this client's camera by that id and asks it for its picture every frame.
- **Two flags: `Destroyed` and `PluggedIn`, and `Offline` is either.** The host sets `Destroyed` from `Health` damage (`Component.IDamageable`); the player flips `PluggedIn` from the camera's own menu. Both sync, and an offline camera stops looking at the world and gives television static instead: a 320×180 `Color32` buffer uploaded once per rendered frame (up to 60 a second) with a bright band rolling down it. The app's badge says **NO SIGNAL** where it says LIVE, the camera's LED is red while it works and black when it does not, and its gizmo is drawn red. Only a destroyed camera throws sparks and crackles.
- **A camera is worked like any other object**: `SecurityCamera` makes its own `Interactable` on `OnStart` and answers as an `IInteractionHandler` with `power` (Unplug/Plug in) and `repair` (hidden unless destroyed) — see [security.md](docs/security.md).
- One 640×360 texture per camera, twelve pictures a second, 16 by 9, kept until the object goes: the grid and the enlarged view scale the same picture, so a camera never holds two.
- Placing the prefab is all it takes to add a camera; the app finds them by scanning the scene and keeps the nearest nine. Nothing about a camera is synced to be watched, so it works the same whether the scene placed it or the host spawned it.

## Effects

`Code/Effects/` is for small effects the game makes itself instead of borrowing a particle file. `SmokeEmitter` makes a plume that rises and fades; `SparkEmitter` throws electric sparks that fall and crackle out. Both are drop-on-anything components — an emitter with a rate or an interval, a tint, sizes, and a `Sprite` to override the picture they make themselves — and both are a thin wrapper over the engine's own particle system: they build a `ParticleEffect` with a `ParticleSpriteRenderer` and a `ParticleSphereEmitter` on their GameObject and map their properties onto it, so nothing is a GameObject per particle. See [effects.md](docs/effects.md).

- **Nothing about a particle is saved or sent**: each one is made on the client that sees it, like a camera's feed, so `Emitting` is not synced and its owner sets it from something that is.
- **`Lighting` and `Shadows` off on the renderer**, and a sprite that fills its own square: the engine's sheets are mostly empty and a soft disc that fades all the way through reads as a smudge.
- **`ForceScale` is in hundreds of units a second squared** and `Duration = 0` with `Loop` means for ever; a one-second loop leaves a gap in a plume. Both emitters’ `Rise`/`Gravity` are divided by 100 on the way in.
- **Sounds are assets, effects are code.** `SparkEmitter` plays `sounds/effects/sparks.sound` when it starts emitting and then every `CrackleGap` (5 s); the takes behind it are generated by `tools/audio/make_spark_crackle.py` and committed as wavs.
- **`SoundEvent.UI` means 2D**, not "interface": with it on a sound has no position and no distance attenuation, which is how a crackle ended up audible across the map. A world sound needs it off. The emitter also sets the 3D options per play on the `SoundHandle` (`SpacialBlend`, `OcclusionEnabled`, `AirAbsorption`, `ReverbEnabled`, `Distance`), so `HearingRange` is the emitter's and not the asset's.
- A destroyed security camera sparks: `SecurityCamera.EnsureSparks` makes or finds its emitter and sets `Emitting` to `Destroyed` every frame; an unplugged one is only off. It smoked before that — the smoke component is still there for anything that wants it.

## The Wired

The Wired is in the same scene as the real world, under the map. `WiredTravel.Cross( connection )` (host only, from The Wired app, for the player in the seat) teleports the player to a random object tagged `spawn_point_wired` and back to where they were; `PlayerData.InWired` says which. `WiredWorldSystem` dresses each client's own view for its own player: every skybox component (2D or 3D) on an object tagged `wired` is on and every other one is off (found by component, not by tag: the map makes its own objects at load, so a tag set on one in the editor is lost at Play), and the main camera excludes the tag `map` while in the Wired and the tag `wired` at home, so neither draws the other's world. Apps ask `WiredTravel.PlaceOf( seat )`, never the scene. The crossing fades the traveller's screen to black (`ScreenFade`, a HUD layer above the rest, put on the HUD object by `HudSystem`, with the highest `z-index`; `GameManager.Fade` asks one player's client), moves them while it is black, and fades back in.

## Security

**Always think about privilege escalation attacks.** For every change to Navi, ask how an app could use it to get permissions or root it wasn't granted, to act as another app, or to act without the player's consent. Assume Store apps are written by a stranger who wants that.

- **Consent prompts live only in the secure layer** (`NaviSecurePrompt`), like Windows' secure desktop:
  - It is its own panel, in front of the screen, so it draws above everything and gets clicks first.
  - While a prompt is open it covers the screen, so apps can't be clicked.
  - Apps can't reach it through their panel's ancestors.
  - Its controls react only to a real mouse press (`Input.Keyboard.Down( "MOUSE1" )`, which game code can't fake), made after the prompt has been up for `ArmTime`, and released on the same control.
  - Never show a consent prompt in the desktop or in an app panel, and never add a way to answer one without real player input.
- **The lock screen lives in the secure layer too.** While `NaviComputer.IsLocked`, `Authorize` refuses every `User…` RPC except sit, keep-seat, leave and unlock. Without a password the player who locked it unlocks with a real press (`LockOwner`). With a password or pattern (`NaviLockKind`), it is typed or drawn only in `NaviLockEntry`, inside the secure layer, on the client of the player in the seat: it is never synced, never shown to anyone else, and never sent. The client turns it into a proof (`NaviLockCrypto`: salted PBKDF2-HMAC-SHA256) and only that goes to the host with `UserUnlockWith`/`UserSetLock`; the host keeps the salt and a hash of the proof, and the hash never leaves it (`CaptureSave( secrets: false )` for snapshots). Wrong tries are counted and delayed by the host for each connection, so one player's guesses never make another wait. While one is typed, `SecureEntryActive` stops the player's keys being forwarded to any app. Not protected: hostile code in the game (see the known limit below) can read the client's memory, or change the host's state.
- **App calls go through `NaviSystemCalls`**, which runs as the calling window. Check permissions there. Never trust what an app says about who it is, and don't give apps a reference to Navi objects.
- **Multiplayer: the host runs the computer.** Clients only draw its snapshot. What a player does on the screen reaches the host as a `User…` RPC on `NaviComputer`, which must check the caller is the seated user (`Authorize`, from `Rpc.Caller`). Never let a client send state, make app calls, or answer a prompt without the seat. A viewer's copy of a shared app makes no calls, except the two that only change its own client (`window.local-title`, `input.keep-local`, answered in `NaviAppHost`).
- **The Web Browser's tabs, address, history, page title and typed keys stay on the seated player's client.** The page loads in the player's real browser engine, so an address someone else chose could send them to any site, such as an IP logger. The app is Shared only for Dino Run (`WebBrowserSharedViewModel`, on the host); browsing is the seated player's own copy (`WebBrowserViewModel`, one per tab in `WebBrowserTabs`, up to eight, each with its own `WebPanel`), which publishes nothing, sets only a local title, and keeps its keys local (`Navi.Input.KeepLocalAsync`) so no shortcut or input action reaches the host. Other players see a private screen. Never publish any of it or take an address from outside. Local addresses (`browser://`) and file addresses (`file:///Pictures/x.png`, the computer's own files, read with `navi.files.access`; a seated client's copy reads them from the host, see the Files bullet) are drawn by the browser itself and open only when typed or clicked in its own pages: a web page that goes to one is sent back, so no site can open them or show the player's real files; the host learns only whether the player is on `browser://dino`, so the game can be shared.
  - Known limit: the host trusts the user's client that a prompt answer came from a real press. A modified client can fake it, for its own seat only. A hostile host can make clients download any Store app, and open any panel class in their code as an app (clients without the game's `.napp` files take the host's manifests).
- **Hardware is the game's to install, and only on the host** (`NaviComputer.InstallHardware`, `RemoveHardware`). Never add an app call or `User…` RPC that installs, removes or fakes hardware; apps only read it. Every call that reaches another computer, a server or the internet calls `NaviNetwork.Require( computer )` first, and game code that connects two computers uses `NaviNetwork.Reach`, which refuses unless both are online. Sound calls never throw: without a sound card they answer false. A seated client's app sounds reach others only through `UserPlaySound`, which checks the caller is the seat's user and rate-limits; the broadcast RPCs are `HostOnly`. Known limit, as for every app: an app's code can call the engine's web, HTTP or sound itself.
- **Plugins are part of the OS, and only the host installs them** (`NaviPluginManager`). They run with no sandbox, permissions or prompt, so the host's choice is the only gate: never add a way for a client, an app or a `User…` RPC to install, remove or toggle one, and keep the console commands refusing to run unless `NaviPluginManager.CanManage`. Clients run the plugins the host announces.
- **Files: an app without `navi.files.access` has only its own folder** (`/Library/Apps/{app id}`). `NaviFileCalls` checks every path twice: as the app wrote it, before anything is looked up (so it can't learn what exists outside), and where it leads with symlinks followed (so a link in its folder can't reach out). Any new `files.*` call must do both. A client's copy of an app reads the host's files only through `NaviComputer.ReadRemoteFiles` (`UserReadFiles`): only the reading calls in `RemoteFileCalls`, only from the seated user (`Authorize`, so never while locked), run on the host as an open window's own process through `NaviFileCalls`, size- and rate-limited, and answered to the caller alone. A client watching the screen may only ask for thumbnails (`UserWatchThumbnail`), and only of the pictures in the folders a shared app's host copy listed last (`FolderListed`): never let a watcher read a file or reach a thumbnail of something the screen doesn't show. The one other thing a watcher may ask for is the preview (`files.preview`, at most 1600 px) of the single picture a shared app's host copy asked for last (`shownPreview`: the Image Viewer's open image), which the screen shows at that size anyway. Never add a call that writes, moves or deletes to that list, and never take permissions or an app id from the client beyond naming an open window. Restoring from the trash and ejecting a drive need the permission. Only the host has the files; they are never sent to clients.
- **The file picker is a system window, not part of the app.** `Navi.Files.PickAsync` (`files.pick`, no permission needed) makes the computer open the File Picker (`navi/apps/filepicker.napp`, a core app: root, never in the start menu, no app can `apps.launch` it, always opaque). Only that app may make the `picker.*` calls (`NaviSystemCalls` checks the caller's id), and they only answer the one request waiting (`NaviComputer.Picker.cs`). The chosen file goes into the caller's `NaviProcess.PickedFiles`, which `NaviFileCalls` honours for **reading that exact path only** (`read: true`, never write, move or delete, never its folder or its siblings). The caller only gets a path back; it never sees a folder listing. Closing the picker or the caller answers with null. Never let an app pass a path to `picker.choose`, add a way to grant `PickedFiles` outside `AnswerPick`, or draw the picker inside an app's panel. Known limit, as for every window: hostile code in the game can fake the choice (it can already change the computer's state).
- **Messages belong to a player, not to an app or a computer.** `NaviMessages` keeps them on the host. Every `messages.*` call (`NaviMessageCalls`) needs `navi.messages.access`, runs on the host, and is asked as the player in the computer's seat, worked out from the connection (`NaviMessages.Identify`). Never take the player, or a "from", from an app's arguments, and never add a call that reads a thread or sends as a player other than the seat's. Messages are saved on the host and never sent to clients except as a shared app's state (the open conversation), which every player near the screen gets.
- **Game NPCs in Messages are the game's voice** (`NaviNpcs`). Only game code makes them and speaks for them (`NaviNpc.Send`, `Edit`, …); no `messages.*` call or `User…` RPC may send as an NPC, edit or delete its messages, or register one. An app may message an NPC as the seated player, and the text that reaches `NaviNpc.Received` is that player's: the game must not trust it. A hidden NPC refuses a player's message until it has written to them first.
- **Drag and drop is the desktop's, on the player's client** (`NaviComputer.Drag.cs`, `NaviDesktop.UpdateDrop`, `docs/app-architecture.md`). `drag.begin` is answered in `NaviAppHost` (any copy, never sent) and refuses unless the player really holds the mouse (`Input.Keyboard.Down( "MOUSE1" )`), is the unlocked user, and the source has `navi.files.access` for a `files` offer; paths, text and label are cleaned there. The desktop finds the drop zone (a panel an app marked with `AcceptDrops`) under the mouse, picks the effect, draws the ghost, and tells the zone's app enter, over, leave and drop when the real button is let go; the source hears how it ended. A drop is a payload only and grants nothing: the target reads paths with its own permissions. Never add a way for an app to start a drag without a press, drop by itself, or give a drop file access (unlike the picker's `PickedFiles`).
- **Notifications are drawn by the desktop.** An app gives only a title and text (`navi.notifications.post`); its name and icon come from its manifest, so it can't pass for another app or the system. It dismisses only its own, and can't unmute itself (core apps can, as the OS).
- **Store apps are untrusted.** Only pre-packaged apps are part of the OS. A Store app gets root only after the player accepts it in the secure layer.
- **Run-time scripts (`Game.Scripting`, Breen) see every public member of every type in the game and Navi** (`docs/scripting.md`). Only `private` and `internal` members are hidden: not `internal` classes, not `[Hide]`. Never run a script from a player or a Store app unless it goes through a guard that makes sensitive public methods refuse while it runs, and nothing else calls `Game.Scripting`. Navi has one: `NaviScriptGuard` (`NaviComputer.RunScript`, the only caller of `Game.Scripting`), and Code Edit's Run button uses it, behind `NaviComputer.ScriptingEnabled` (off by default) and the `navi.scripts.run` permission. The guard is a list of public methods that refuse while a script runs, not a wall: **any new public method on `NaviComputer` or other Navi types that changes state or leaks a secret must check `NaviScriptGuard.Active`**, and player types (health, position, weapons) are not guarded at all.
- **Known limit: s&box gives every package's code the same sandbox.** `TypeLibrary` exposes even private members of package (`package.*`) code, so a hostile Store app can find `NaviComputer` and change its state directly, skipping permissions and prompts.
  - Navi's permissions stop honest-but-careless apps and UI tricks: fake clicks, overlays, pre-ticked boxes. They don't stop hostile code. Don't claim more than that in UI or docs.
  - What helps against hostile code: the Store's official badge, published code being readable, and the root consent at install.

## Architecture

s&box uses a scene/GameObject/Component model. Gameplay is written as `Component` subclasses that override lifecycle hooks (`OnUpdate`, `OnFixedUpdate`, `OnPreRender`, …). Movement is handled by the engine's built-in `PlayerController` with `MoveMode*` components. A custom component can drive it by setting `WishVelocity` / `EyeAngles` and pull it in with `[RequireComponent]`.

### How systems find and react to each other

- **Find a player's parts with `Players`** (`Code/Game/Players.cs`): `Players.LocalController`, `Players.LocalObject`, `Players.Local<T>()` and `Players.For<T>( connection )`. Every player component is on the player prefab, so any of them can be asked for. Don't write another `GetAll<…>().FirstOrDefault( x => !x.IsProxy )`.
- **React to a change with a scene event, not by polling.** Implement the interface on a component: `Global.IPlayerEvents` (spawn, damage, death, kills), `Global.IProgressEvents` (a `PlayerProgress` loaded or changed, with `ProgressChange` flags saying what; host only) and `Global.IInventoryEvents` (slots changed, item dropped). A new system that others may care about posts its own `Global.I…Events`, the same way.
- **Redraw with one `Version`.** `PlayerProgress`, `PlayerInventory` and `AbilityLoadout` each bump a `Version` on every change; a panel or view model hashes it in `BuildHash` or its signature.
- **The game's own Navi apps find their seat with `GameAppSeat`** (`UserOf( panel )`, `ComputerOf( panel )`), never from what an action says.

### Static state and hot reload

**Never make static state that changes at run time `readonly`, including get-only auto-properties (`{ get; } = new()`).** A hot reload resets a `static readonly` field to its initial value when its type holds only engine or BCL types (`string`, numbers, `HashSet<string>`, `Dictionary<string, long>`). Fields that aren't readonly keep their values, and so do readonly ones that hold the assembly's own types. Use `static Dictionary<…> x = new()` or `{ get; private set; } = new()`. Constants (lookup tables nobody changes) can stay readonly, since a reset only picks up edits. Instance fields aren't affected: a readonly instance field keeps its value.

Losing such a field fails silently. Navi lost its map of downloaded Store apps this way, so installed Store apps vanished from the start menu, and it also lost the game's Store allowlist. To check a change, set the state, force a reload (edit a file in the same assembly), and read it back with `sbox-cli --call run_csharp`.

### UI pitfalls

Found building the Character menu (`Code/Character/`). Each one froze the editor, closed the menu at once or left the player without controls.

- **A `ScenePanel` with no `RenderScene` ticks the game scene**, which runs the panel's own component again, in itself. Build the scene before the panel exists and pass it as an attribute (`<ScenePanel RenderScene=@scene/>`). Never destroy a scene while a panel still draws it.
- **A `new Scene()` starts every `GameObjectSystem` in it**, so a system that makes a HUD makes one there too (a second menu that shares `static` state and closes the first). Skip it: see `Hud.Applies` (`CharacterMenu.PreviewScene`).
- **`Input` mouse buttons read false while the cursor is over a panel that takes the mouse**, and `HasActive`/`HasHovered` can stay false. Use the panel's events (`@onmousedown`, `@onmouseup`, `@onclick`), as `AbilityMenu` does.
- **A panel's event handlers and its component's `OnUpdate` were not on the same instance.** State they share must be `static`.
- **Turning off `UseInputControls` leaves `WishVelocity` as it was**, so a held key walks on. Set `WishVelocity = 0` every frame while it is off, as `NaviInputCapture` does.
- **Removing a `GameObjectSystem` class** makes the open editor log an error every frame until it restarts.
- **The editor's console buffer and `sbox-dev.log` lag behind a hang.** To debug one, write lines to `FileSystem.Data` at once (the game's data folder under the engine's `data/`), and remove them when done. Tests that call private methods through `run_csharp` can freeze the editor: press the real key.

## Code style

`docs/code-style.md` is the contract: Rider's **default** code style settings over the repo's `.editorconfig`, which is what formats the files in `Code/`, `Editor/`, `Addons/` and `Libraries/navi/Code/`. Run Reformat Code (Ctrl+Alt+L) on the files you touch before committing.

- Tabs, 4 wide, CRLF, final newline. Braces on new lines (Allman).
- Spaces inside parentheses for calls and control flow, e.g. `Input.Down( "Run" )`, `if ( x > 0 )`; no spaces inside casts, grouping parens, `nameof(...)` or target-typed `new(...)`.
- Razor inline expressions are spaced: `@( entry.Expanded ? "Less" : "More" )`.
- 120 columns. The doc covers where a line breaks and how: Razor attributes wrap aligned under the first attribute, LINQ chains get one call per line, collection expressions open on the next line.

## Git commits

When you finish a piece of work, commit it, without waiting to be asked. Stage only the files you changed for that work, never unrelated changes already in the working tree. Format the files you touched first (see Code style).
